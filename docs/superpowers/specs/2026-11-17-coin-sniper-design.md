# Coin Sniper 설계 — 바이낸스 데모 모드 기준

- 작성일: 2026-11-17
- 기준 원본: `rundevelrun/quant-sniper` main `cd6dc66` (키움증권 한국 주식 봇)
- 상태: 초안, 승인 대기

표기 규칙: **[결정]** 은 대화에서 사용자가 정한 것, **[제안]** 은 작성자가 정한 기본값으로 사용자가 바꿀 수 있는 것,
**[확인 필요]** 는 0단계에서 실제 호출로 검증해야 하는 것이다.

---

## 1. 의도

원본 봇의 컨셉(사람 배제, 확인 안 되면 주문 안 함, 체결 기준 장부, 생존 우선)과 매매 룰, 리스크 골격을 그대로 따르는
**코인 현물 자동매매 봇**을 만든다. 먼저 바이낸스 현물 데모 모드에서 가짜 잔고로 몇 주~몇 달 돌린다.

데모 기간이 끝나면 사용자는 **수익률**과 **오류율** 두 가지를 보고 실전 전환 여부를 판단한다. **[결정]**
따라서 이 두 지표를 끊김 없이 쌓고 보여 주는 것이 봇을 돌리는 것만큼 중요하다.

## 2. 목표, 비목표, 실패 조건

### 목표 (1단계)

1. 바이낸스 현물 데모 모드에서 24시간 무인으로 도는 봇.
2. 원본과 같은 형태의 대시보드에 수익률·오류율 섹션을 더한 것.
3. 주소와 키만 바꾸면 실전으로 전환되는 구조. 단, 실전 실행은 1단계 범위가 아니다.
4. 전략·리스크 코드가 거래소와 시계를 모르는 순수 함수라서 2단계 백테스트가 같은 코드를 쓸 수 있을 것.

### 목표 (2단계, 이 문서는 개요만)

5. 같은 전략·리스크 코드로 과거 데이터 백테스트. 데모 몇 달로는 거래 표본이 적어 수익률 판단이 약하기 때문이다.

### 비목표

- 선물, 마진, 레버리지, 공매도. 현물 롱 전용이다. **[결정]**
- 원화 마켓, 다른 거래소. 어댑터 경계만 만들어 두고 구현은 바이낸스 하나다.
- 실전 자금 운용, 입출금 자동화.
- 웹 UI. 대시보드는 원본처럼 마크다운과 JSON이다.
- 전략 추가나 최적화. 원본의 두 전략(RSI 과매도 회복, 변동성 돌파)만 옮긴다.

### 실패 조건 (동작해도 실패로 본다)

- 데모 장부와 실전 장부·키가 섞일 수 있는 구조.
- 시세·계좌·체결 중 하나를 확인하지 못했는데 신규 주문이 나가는 경우.
- 오류가 조용히 삼켜져 오류율에 잡히지 않는 경우.
- 봇이 죽었다 살아났을 때 포지션, 최고가, 보호선, 계좌 고점을 잃는 경우.
- 주문은 나갔는데 장부에 없거나, 장부에는 있는데 거래소에 없는 상태가 감지되지 않는 경우.

## 3. 제약

- Python 3.10 이상. 윈도우와 리눅스 양쪽에서 실행된다. **[결정]** (원본은 `fcntl` 때문에 리눅스 전용)
- 의존성은 원본처럼 최소로 한다. REST는 표준 라이브러리, WebSocket은 `websockets`. **[제안]**
  ccxt를 쓰지 않는 이유: 필요한 호출이 열 개 안팎이고, 데모 모드 주소 지원 여부를 따로 확인해야 하며,
  원본의 "표준 라이브러리만" 원칙과 맞다.
- 바이낸스 데모 모드는 "실거래소와 유사한 시세"이지 동일하지 않다(공식 문서 명시). 슬리피지 수치는 참고용이다.
- 데모 모드는 점검 시간에 주문·취소가 안 된다. 점검은 장애가 아니라 정상 상황으로 다뤄야 한다.
- 이 저장소의 새 브랜치에서 작업한다. 대시보드는 `origin`의 `dashboard` 브랜치에 올린다. **[결정]**
  `origin`은 사용자 포크(`bangddong/quant-sniper`)이고 지금 `dashboard` 브랜치가 없다. 원본 주식 봇은
  `rundevelrun/quant-sniper`에 게시하므로 서로 덮어쓰지 않는다.
- 이식 기준은 원본 `cd6dc66`이다. 로컬 main은 그보다 6커밋 뒤처져 있으므로 원본 최신을 받아서 옮긴다.
- 1단계 동안 원본 파일(`bot.py`, `kiwoom_*.py`, `tests/` 등)은 건드리지 않고 참고용으로 둔다. **[제안]**
  그래서 새 진입점은 `coin_bot.py`, 새 테스트는 `tests/coin/`에 둔다.

## 4. 검토한 접근

| 접근 | 내용 | 장점 | 단점 |
|---|---|---|---|
| 1. 교체만 | `bot.py` 단일 루프 유지, `kiwoom_*.py`만 바이낸스로 | 가장 빠름, 원본과 1:1 비교 | 장 시간·갭·거래일이 루프 곳곳에 박혀 있음. 백테스트에 재사용 불가 |
| **2. 재조립** | 룰·리스크 함수는 살리고 구조를 분리 | 봇과 백테스트가 같은 코드 사용. 데모↔실전이 설정 전환 | 초기 작업량이 더 많음 |
| 3. 프레임워크 | Freqtrade 등에 룰만 얹기 | 백테스트·통계·화면이 이미 있음 | 낙폭별 주문 축소, 위험 기준 수량, fail-closed가 프레임워크 방식으로 변형됨 |

**선택: 2번.** **[결정]** 판단 기준이 수익률이라 백테스트가 필요하고, 그러려면 전략 코드가 루프에서 분리돼 있어야 한다.
원본 컨셉을 참고한다는 목적에도 가장 맞다.

## 5. 구조

```text
coin_bot.py                 실행 진입점 (설정 검증 → 잠금 → 엔진 시작), 수동 정리 명령
bot.py, kiwoom_*.py ...     원본 주식 봇 (참고용, 수정하지 않음)
coin_sniper/
  config.py                 파라미터와 환경변수, 모드 선택
  strategy.py               지표와 진입 신호            (순수 함수, 원본에서 이식)
  risk.py                   수량 산정, 낙폭 제어, 손절 래칫, 열린 위험 합계  (순수 함수, 원본에서 이식)
  universe.py               감시 종목 선정              (순수 함수)
  exchange/
    base.py                 거래소 인터페이스
    binance.py              바이낸스 REST 구현 (서명, 재시도, 오류 분류)
    binance_feed.py         바이낸스 시세 WebSocket
    fake.py                 테스트용 가짜 거래소
  ledger.py                 포지션·체결·위험 상태·주문 의도 저장 (원자적 JSON)
  metrics.py                오류 카운터, 계좌 평가액 기록
  dashboard.py              렌더링과 dashboard 브랜치 게시
  engine.py                 루프: 위 조각을 순서대로 호출
  backtest.py               2단계
state/<mode>/               런타임 상태 (git 추적 제외)
tests/coin/                 새 테스트 (원본 tests/는 그대로 둔다)
```

핵심 경계는 둘이다.

- **전략·리스크는 거래소도 현재 시각도 모른다.** 캔들, 가격, 잔고, 시각을 인자로 받는다.
- **엔진은 거래소 구현을 모른다.** `exchange/base.py`의 인터페이스만 쓴다.

### 5.1 거래소 인터페이스

| 기능 | 용도 |
|---|---|
| 종목 규칙 조회 | 수량 단위, 가격 단위, 최소 주문 금액, 거래 가능 상태 |
| 일봉 조회 | 지표 계산. 하루 한 번 받고 당일 봉은 실시간 시세로 덧붙인다(원본 방식) |
| 계좌 조회 | 자산별 사용 가능·잠긴 수량 |
| 시장가 매수·매도 | 봇이 만든 주문 식별자를 붙여 보낸다 |
| 주문 조회 | 식별자로 체결 수량, 체결 금액, 수수료(어느 자산으로 냈는지 포함) 확인 |
| 보호 손절 주문 등록·취소 | 거래소 측 손절 |
| 미체결 주문 조회 | 재시작 시 대조 |
| 서버 시각 | 서명 요청의 시각 보정 |
| 시세 피드 | 종목별 현재가·당일 시가·고가·저가·거래량, 수신 시각, 연결 상태 |

모든 호출은 성공·실패를 값으로 돌려준다. 실패는 **일시적**(네트워크, 5xx, 호출 한도, 점검)과
**확정적**(잔고 부족, 규칙 위반, 인증 오류)으로 분류해서 돌려준다. 엔진은 이 분류로 재시도와 중단을 정한다.

### 5.2 모드와 격리

- `MODE=demo|live`. 기본값은 `demo`.
- 모드별로 주소, 키 환경변수(`BINANCE_DEMO_*`, `BINANCE_LIVE_*`), 상태 디렉터리(`state/demo`, `state/live`)가 따로다.
- `live`는 원본처럼 `LIVE_TRADING_ENABLED=true`가 추가로 있어야 실행된다. 없으면 실행을 거부한다.
- 대시보드 맨 위에 현재 모드를 크게 표시한다.
- 모의 체결 경로는 만들지 않는다. 데모 모드가 그 역할을 한다(원본의 "가상 체결 경로 없음" 원칙 유지).

## 6. 매매 룰

원본 룰을 유지하되, 주식 시장에만 있는 개념은 아래처럼 바꾼다.

### 6.1 시간

- 내부 시각은 전부 UTC. 대시보드 표시는 KST.
- **하루 경계는 UTC 0시**(한국 오전 9시), 바이낸스 일봉 기준. **[결정]**
  감시 종목 선정, 일일 손실 기준 평가액, 당일 봉이 모두 이 시각에 바뀐다.
- 장 열림·닫힘 개념은 없다. 대신 "시세가 신선한가"와 "거래소가 주문을 받는가"로 매매 가능 여부를 정한다.

### 6.2 감시 종목 **[제안]**

원본: 전일 거래대금 상위 중 시총 1조–5조 원, 경고 종목 제외, 최대 20종목.
코인: 거래소 API에 시총이 없으므로 거래대금과 제외 규칙으로 대신한다.

- 대상: USDT 현물 마켓 중 거래 가능 상태인 종목.
- 제외: 스테이블코인과 법정화폐 연동 코인, 레버리지 토큰, 설정의 제외 목록.
- 조건: 일봉이 70개 이상(신규 상장 제외), 전일 거래대금이 하한 이상(잡코인 제외).
- 순위: **전일(완료된 UTC 하루) 거래대금** 기준 상위 20. 진행 중인 24시간 값은 쓰지 않는다(원본의 "전일 확정 데이터" 원칙).
- 비트코인과 이더리움은 감시 종목에 포함한다. 원본은 대형주를 뺐지만 코인은 시총을 모르고, 설정의 제외 목록으로 뺄 수 있다.
- UTC 0시 직후에 하루 한 번 선정한다. 실패하면 기본 목록으로 대체하지 않고 그날 신규 매수를 막는다(원본과 동일).
- 감시 종목에서 빠진 보유 종목도 청산될 때까지 계속 감시한다(원본과 동일).

### 6.3 진입

- **시장 필터**: 비트코인(BTCUSDT)이 상승 중인 60일 이동평균선 위에 있을 때만 진입. **[결정]** KODEX 200 자리를 대신한다.
- **전략 1, RSI 과매도 회복**: 원본 조건 그대로(전 봉 RSI 28 이하 → 30 상향, 양봉, 전 봉 고가 돌파).
- **전략 2, 변동성 돌파**: 원본 조건 그대로(당일 시가 + 전일 변동폭×0.5 돌파, 20일선 위이고 20일선 상승, 거래량 확인).
  거래량 확인의 "장중 진행률"은 UTC 하루 중 경과 비율로 바꾼다.
- **가격 품질 필터**: 갭 필터는 없앤다(24시간 연속 시장이라 갭이 없다). 당일 급등 제외와 윗꼬리 제외는 유지하고 수치만 바꾼다.
- **진입 시간**: 제한 없음. 단 UTC 0시 직후 15분은 진입하지 않는다(원본의 "장 시작 15분 제외"와 같은 취지). **[제안]**
- **신호 확인**: 같은 종목·전략 신호가 30초 간격 3회 연속 유지돼야 주문(원본과 동일).
- **주문 직전**: 실시간 시세를 다시 확인하고, 오래된 시세면 건너뛴다(원본과 동일).

### 6.4 수량과 계좌 보호

- **봇 자본은 가상 계좌로 관리한다.** **[제안]**
  - 봇 현금 = 시작 자본(설정값) + 누적 실현 손익 − 현재 보유 포지션의 매수 금액.
  - **계좌 평가액** = 봇 현금 + 보유 포지션의 현재 평가액. 수량 산정, 일일 손실, 낙폭, 수익률의 기준이다.
  - 시작 자본 기본값은 **1,000 USDT**다. 실전에서 굴릴 금액과 비슷하게 맞춰야 최소 주문 금액에 걸리는 빈도와
    슬리피지가 실전과 비슷해진다. **사용자가 정할 값이다.**
  - 주문 가능 금액은 봇 현금과 거래소의 실제 사용 가능 USDT 중 작은 쪽이다.
    실제 USDT가 봇 현금보다 적으면 위험 이벤트로 남긴다.
  - 봇이 사지 않은 자산과 시작 자본을 넘는 잔고는 평가액에도 대조에도 넣지 않는다. 데모 계정에 기본 지급되는
    큰 잔고나 실전 계정에서 따로 보유한 코인 때문에 계산이 틀어지거나 매매가 멈추는 것을 막기 위해서다.
- 수량 = 아래 셋 중 최솟값을 종목의 수량 단위로 내림. 최소 주문 금액에 못 미치면 건너뛴다.
  - 거래당 위험 한도: 평가액 × 0.7% ÷ (진입가 × 손절폭)
  - 종목당 한도: 평가액 × 30%
  - 사용 가능 USDT
- 최대 동시 보유 3종목(원본 최신값).
- **열린 위험 합계 한도**: 보유 포지션들의 "지금 손절되면 잃는 금액" 합계가 평가액의 일정 비율을 넘으면 신규 진입을 막는다. **[결정]**
  원본의 업종 제한을 대신한다. 코인은 업종보다 비트코인 동조가 문제이기 때문이다. 계산 방식은 아래와 같다. **[제안]**
  - 포지션별 위험 = max(0, 매수가 − 현재 보호선) × 수량. 보호선이 매수가 위로 올라간 포지션은 0이다.
  - 판정은 "기존 합계 + 신규 포지션의 계획 손실"로 한다.
  - 한도를 넘으면 진입을 막지 않고 **남은 한도에 맞춰 신규 수량을 줄인다.** 줄인 결과가 최소 주문 금액 미만이면 건너뛴다.
  - 예: 0.7% 위험 포지션 둘을 보유 중이면 세 번째는 0.6%까지만 들어간다.
- 일일 손실 -4%에 그날(UTC) 신규 주문 중단. 고점 대비 -8%에 주문 크기 절반, -12%에 신규 매수 중단(원본과 동일).

### 6.5 청산

구조는 원본 그대로다. 손절선은 올라가기만 하고 내려가지 않는다.

1. 초기 손절: ATR(14) × 1.5, 하한과 상한 사이로 제한.
2. 1차 목표 도달 시 보호선을 매수가 위로 올림.
3. 2차 목표 도달 시 고점 추적 시작. 진입 후 최고가 대비 ATR 기반 폭만큼 내려오면 전량 청산.
4. 보유 기간 초과 시 타임스탑. **달력 기준 7일**(진입 시각부터 168시간)로 센다. 원본은 거래일을 세지만 코인은 휴장이 없다.

### 6.6 이중 손절 **[결정]**

봇이 죽어도 보호되도록 손절을 두 겹으로 둔다.

- **1차, 봇 감시**: 루프마다 현재가를 보고 손절선 아래면 시장가 매도. 원본 방식이며 래칫과 고점 추적은 여기서 한다.
- **2차, 거래소 손절 주문**: 매수 체결 직후 초기 손절가에 거래소 손절 주문을 건다. 봇이 멈춰 있어도 거래소가 실행한다.
- 봇이 먼저 팔 때는 **거래소 손절 주문을 취소한 뒤** 시장가 매도한다(걸려 있는 주문이 수량을 잠그기 때문).
  취소에 실패하면 매도하지 않고 중단 상태로 들어가 다음 루프에서 다시 시도한다.
- 보호선이 올라가면 거래소 손절 주문도 다시 건다. 호출을 아끼기 위해 일정 폭 이상 움직였을 때만 한다.
- 거래소 손절이 먼저 체결된 것을 발견하면, 그 체결 내역으로 장부에 매도를 기록한다(사유: 거래소 손절).
- 보호 주문이 걸려 있어야 할 포지션에 주문이 없으면 다시 걸고, 그 사실을 위험 이벤트로 남긴다.
- **[확인 필요]** 데모 모드가 손절 주문을 받는지. 안 되면 봇 감시만으로 가고, 그 한계를 대시보드에 상시 표시한다.

### 6.7 초기 수치 **[제안]**

코인 변동성에 맞춘 **출발값**이다. 검증된 값이 아니며 2단계 백테스트로 다시 잡는다. 전부 `config.py`에 둔다.

| 항목 | 원본(주식) | 코인 출발값 |
|---|---|---|
| 초기 손절 범위 | 2.5%–4.0% | 4%–10% |
| 보호선 상향 | +4%에서 매수가 +1% | +6%에서 매수가 +1.5% |
| 고점 추적 시작 | +8% | +12% |
| 추적 폭 | 2%–4% | 4%–8% |
| 당일 급등 제외 | 10% 초과 | 15% 초과 |
| 윗꼬리 제외 | 40% 초과 | 40% 초과 |
| 거래당 위험 | 0.7% | 0.7% |
| 종목당 한도 / 최대 보유 | 30% / 3 | 30% / 3 |
| 열린 위험 합계 한도 | 없음(업종 2종목 제한) | 2.0% |
| 시작 자본 | 실계좌 평가액 | 1,000 USDT (사용자가 정할 값) |
| 일일 손실 / 낙폭 감속 / 낙폭 중단 | -4% / -8% / -12% | 동일 |
| 타임스탑 | 7거래일 | 7일(168시간) |
| 감시 종목 수 | 20 | 20 |
| 루프 주기 | 30초 | 30초 |
| 비용 가정 | 왕복 약 0.41% | 수수료는 실제 체결값 사용, 슬리피지 추정 편도 0.1% |

원본의 손절 범위(2.5–4%)를 그대로 쓰지 않는 이유: 코인 일봉 ATR은 그보다 훨씬 커서 항상 상한에 걸리고,
평범한 흔들림에 계속 손절된다. 거래당 위험 0.7%는 그대로이므로 손절폭이 넓어지면 수량이 자동으로 줄어든다.

## 7. 주문과 장부

### 7.1 주문 절차

1. **의도 기록**: 주문 식별자를 만들고, 종목·방향·수량·사유와 함께 장부의 "진행 중 주문"에 먼저 저장한다.
2. **주문 전송**: 그 식별자를 붙여 시장가 주문을 보낸다.
3. **체결 확인**: 주문 조회로 실제 체결 수량, 평균 체결가, 수수료를 확인한다. 응답이 없으면 제한 시간까지 다시 조회한다.
4. **장부 반영**: 확인된 체결만 포지션과 체결 기록에 쓰고, 진행 중 주문에서 지운다.

재시작 시 진행 중 주문이 남아 있으면 식별자로 거래소에 조회해서 결과를 반영한다.
주문은 나갔는데 장부에 없는 상태를 없애기 위한 장치다. 원본에는 없다.

### 7.2 체결 처리

- **수수료가 산 코인에서 빠지는 경우**: 장부 수량은 체결 수량에서 수수료를 뺀 **실제 받은 수량**이다.
  이렇게 하지 않으면 매도 때 잔고 부족으로 거절된다.
- **매수 부분 체결**: 체결된 만큼만 포지션으로 기록한다.
- **매도 부분 체결**: 체결된 만큼 매도로 기록하고 나머지는 포지션에 남겨 다음 루프에서 다시 판다.
  나머지가 최소 주문 금액 미만이면 "잔량"으로 따로 적고 포지션을 닫는다.
- **체결 미확인**: 제한 시간 안에 확인이 안 되면 장부에 반영하지 않고 진행 중 주문으로 남긴 채 신규 주문을 멈춘다.
  다음 루프에서 계속 조회한다.
- 손익은 실제 체결가와 실제 수수료로 계산한다. 슬리피지는 "주문 직전 시세 대비 체결가 차이"로 따로 기록한다.

### 7.3 계좌 대조

- 장부에 있는 종목만 대조한다. 거래소 잔고(사용 가능 + 잠김)가 장부 수량보다 허용 오차 이상 적으면 불일치다.
- 불일치면 신규 매수를 막고 해당 종목 매도도 보류한다. 일치하면 자동으로 풀린다.
- 장부에 없는 자산은 무시하되 대시보드에 "봇 관리 밖 자산 있음"으로만 표시한다.
- **불일치가 저절로 풀리지 않는 경우**(데모 잔고 초기화, 사람이 직접 매도)에는 봇이 장부를 스스로 지우지 않는다. **[제안]**
  장부를 추정으로 고치면 "체결 기준 장부" 원칙이 깨지기 때문이다. 대신 사람이 실행하는 수동 정리 명령을 둔다.
  - 명령은 거래소에 없는 장부 포지션을 "수동 정리"로 닫는다. 손익은 계산하지 않고 승률·수익률 통계에서 뺀다.
  - 정리 시점부터 수익률을 새 구간으로 계산하고, 시작 자본을 다시 설정값으로 되돌릴지 물어본다.
  - 대시보드는 이 상태를 "수동 정리 필요"로 표시한다. 이 중단은 사람이 명령을 실행해야 풀린다.

### 7.4 중단과 재개

중단은 사유별로 관리하고, 사유마다 풀리는 조건이 있다. 사유가 하나라도 남아 있으면 신규 매수를 하지 않는다.
**보유 종목의 청산 감시는 어떤 중단에서도 계속한다**(원본과 동일).

| 사유 | 풀리는 조건 |
|---|---|
| 계좌 조회 실패, 시세 끊김, 거래소 점검, 호출 한도 | 다음 확인이 정상이면 즉시(원본 최신판과 동일) |
| 감시 종목 선정 실패 | 재시도 성공 시, 또는 다음 UTC 날짜 |
| 일일 손실 한도 | 다음 UTC 날짜 |
| 낙폭 한도 | 매 루프 다시 계산해서 한도 아래로 회복되면 |
| 계좌·장부 불일치, 체결 미확인, 보호 주문 취소 실패 | 대조가 다시 맞거나 주문 상태가 확정되면. 안 풀리면 수동 정리 명령(7.3) |
| 인증 오류, 설정 오류 | 자동으로 풀리지 않음. 사람이 고치고 재시작 |

### 7.5 저장

- 상태는 `state/<mode>/` 아래 JSON 파일이다. 원본처럼 임시 파일에 쓰고 바꿔치기한다.
- 파일: 포지션, 체결 기록, 진행 중 주문, 위험 상태(계좌 고점, 당일 기준 평가액), 감시 종목, 이벤트, 지표, 평가액 기록.
- **git은 장부가 아니다.** **[제안]** 원본은 체결 기록을 main에 push하고 실패하면 매매를 멈춘다.
  코인 버전은 장부를 로컬에만 두고, 대시보드 게시 실패는 "대시보드 지연"으로만 표시하며 매매는 멈추지 않는다.
  24시간 시장에서 GitHub 장애가 매매 중단으로 이어지는 것을 막기 위해서다.
- 같은 모드로 봇이 두 개 뜨지 않도록 잠근다. 윈도우와 리눅스 양쪽에서 동작해야 한다.

## 8. 대시보드

원본과 같은 방식이다. 세 파일(`README.md`, `dashboard_state.json`, `dashboard_events.json`)을 부모 없는 단일 커밋으로
`origin/dashboard`에 덮어쓴다. `AUTO_GIT_PUSH` 기본값은 `false`다. 저장소가 공개라면 보유·체결 내역도 공개된다.

게시 주기는 원본과 같다. 체결·위험·오류는 즉시, 변화가 있으면 5분, 변화가 없어도 30분마다.

### 구성

```text
# Coin Sniper Dashboard          [DEMO]
> 마지막 갱신: 2026-11-17 19:18:18 KST

1. 현재 상태        상태 / 매매 가능 여부 / 중단 사유 / 보유 수
   시스템 신선도    시세 연결 / 마지막 시세 / 마지막 계좌 조회 / 마지막 정상 루프 / 실행 커밋
   오늘의 감시      기준일 / 감시 종목 표(현재가, 최대 수량, 매수 가능성) / 신호 확인 단계
   위험 관리        낙폭 / 오늘 수익률 / 주문 배율 / 열린 위험 합계 / 남은 슬롯
   보유 포지션      수량 / 매수가 / 현재가 / 수익률 / 최초 손절 / 현재 보호선 / 거래소 손절 주문 상태 / 남은 시간

2. 수익률           (신규)
   기간별           오늘 / 7일 / 30일 / 전체 수익률, 같은 기간 비트코인 보유 수익률
   누적 성과        청산 수 / 승률 / 평균 이익 / 평균 손실 / Profit Factor / 최대 낙폭 / 최대 연속 손실 / 누적 수수료 / 평균 슬리피지
   전략별           RSI 회복 / 변동성 돌파 각각의 거래 수, 승률, 평균 수익률
   주간 평가액      최근 12주 주말 평가액과 주간 수익률

3. 오류율           (신규)
   기간별(24시간 / 7일 / 전체)
   API 호출         총 횟수 / 실패 횟수 / 실패율 (일시적·확정적 구분)
   주문             전송 / 거절 / 체결 미확인 / 부분 체결
   시세             재연결 횟수 / 끊긴 시간 합계
   가동             가동률 / 중단 시간 합계(사유별) / 프로세스 재시작 횟수 / 루프 예외 횟수

4. 최근 7일 이벤트  매수 / 매도 / 스킵 / 위험 / 오류 (원본과 동일, 반복 스킵은 횟수로 합침)
```

### 지표 수집

- **오류 카운터**: 거래소 어댑터가 모든 호출의 성공·실패를 한곳에 보고한다. 날짜(UTC)별로 쌓고 400일 보관한다.
  어댑터를 거치지 않는 호출 경로를 만들지 않는다. 그래야 오류율이 빠짐없이 잡힌다.
- **가동률**: 루프가 정상 완료될 때마다 시각을 남긴다. 기대 루프 수 대비 실제 완료 수로 계산한다.
  봇이 꺼져 있던 시간은 재시작 때 마지막 기록과의 차이로 채운다.
- **평가액 기록**: UTC 0시마다 평가액과 비트코인 종가를 한 줄씩 남긴다. 기간별 수익률과 비교 기준은 여기서 나온다.
- 데모 잔고를 초기화하면 보유 코인이 사라져 계좌·장부 불일치로 잡힌다. 7.3의 수동 정리를 거쳐 새 구간으로 계산한다.
  가상 계좌 방식이라 초기화로 USDT 잔고만 바뀐 경우에는 수익률 기록이 끊기지 않는다.

## 9. 오류 처리 원칙

- 확인하지 못한 것은 "없음"이 아니라 "모름"으로 다룬다. 모르면 신규 주문을 하지 않는다.
- 일시적 오류는 짧게 몇 번 재시도하고, 그래도 안 되면 해당 중단 사유를 건다.
- 호출 한도 응답을 받으면 거래소가 알려 준 시간만큼 쉰다. 무시하고 계속 호출하지 않는다.
- 루프 안의 예외는 잡아서 오류로 기록하고 다음 루프로 간다(원본과 동일). 프로세스는 죽지 않는다.
- 키와 서명은 로그, 대시보드, 이벤트에 남기지 않는다.

## 10. 테스트

- **순수 함수**: 원본 `tests/`의 전략·리스크 테스트를 옮기고, 소수 수량 내림, 최소 주문 금액, 열린 위험 합계, 168시간 타임스탑을 더한다.
- **엔진**: 가짜 거래소로 다음 시나리오를 돌린다.
  정상 매수·매도, 매수 부분 체결, 매도 부분 체결과 잔량, 주문 거절, 체결 미확인 후 복구,
  주문 직후 프로세스 종료 후 재시작, 거래소 손절 선체결 발견, 보호 주문 취소 실패, 보호선 상향 시 재등록,
  계좌 불일치와 자동 해제, 시세 끊김, 점검 중 주문 거절, UTC 날짜 변경, 관리 밖 자산 무시.
- **대시보드**: 렌더링 결과에 키·계정 정보가 없는지, 수익률·오류율 계산이 맞는지.
- **0단계 확인 스크립트**: 데모 모드에 실제로 붙어 아래 "확인 필요" 항목을 점검한다. 자동 테스트와 별개다.

## 11. 진행 순서

**0단계, 데모 모드 확인.** 코드를 쌓기 전에 작은 스크립트로 확인한다. 결과에 따라 설계가 바뀔 수 있는 항목이다.

1. 한국 계정으로 데모 모드 API 키가 발급되는지.
2. 데모 모드가 손절 주문을 받는지, 어떤 종류를 받는지. (6.6이 달라진다)
3. 데모 모드의 종목 수와 거래대금이 감시 종목 20개를 뽑기에 충분한지. (6.2가 달라진다)
4. 시세 WebSocket이 데모 주소에서 당일 시가·고가·저가·거래량을 주는지.
5. 수수료가 어느 자산에서 빠지는지, 최소 주문 금액이 얼마인지.
6. 초기 지급 잔고 구성과 초기화 동작.

확인이 실패했을 때의 처리 **[제안]**:

| 항목 | 실패 시 |
|---|---|
| 1. 키 발급 불가 | 멈추고 사용자에게 보고한다. 테스트넷이나 다른 거래소로 갈지는 사용자가 정한다 |
| 2. 손절 주문 불가 | 봇 감시만으로 진행하고 한계를 대시보드에 표시한다(6.6) |
| 3. 종목·거래대금 부족 | 조건을 통과한 종목만으로 진행한다(20개 미만 허용). 5개 미만이면 멈추고 보고한다 |
| 4. 피드에 당일 값 없음 | 당일 봉을 같은 데모 주소의 REST 캔들 조회로 주기적으로 받아 대신한다 |
| 5, 6 | 관찰한 값을 설정과 문서에 반영하고 진행한다 |

어떤 경우에도 데모 모드에서 실거래소 주소의 시세를 섞어 쓰지 않는다. 모드 격리 원칙을 지키기 위해서다.

**1단계, 봇과 대시보드.** 순수 함수 → 가짜 거래소와 엔진 → 바이낸스 어댑터 → 대시보드 → 데모 가동.

**2단계, 백테스트.** 같은 `strategy.py`, `risk.py`를 과거 일봉에 적용한다. 장중 손절 경로는 더 짧은 봉으로 근사한다.
6.7의 출발값을 여기서 다시 잡는다. 상세 설계는 1단계가 돌기 시작한 뒤 따로 쓴다.

## 12. 만드는 사람에게 맡기는 것

- 함수·클래스 이름과 파일 내부 구성.
- HTTP 재시도 횟수와 간격, 시간 초과 값.
- JSON 파일의 세부 필드. 단 7.5의 종류와 재시작 복원 요구는 지킨다.
- 대시보드 마크다운의 세부 배치. 8절의 항목은 빠짐없이 들어가야 한다.
- 거래소 손절 주문을 다시 거는 최소 변동 폭.
- 스테이블코인·레버리지 토큰 제외 목록의 구체적 내용과 거래대금 하한 값.
- 윈도우·리눅스 단일 실행 잠금의 구현 방법, 실행 스크립트와 서비스 등록 예시.
