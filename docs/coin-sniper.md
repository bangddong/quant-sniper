# Coin Sniper (바이낸스 현물 봇) 운영 안내

이 문서는 저장소 안의 **코인 봇**을 돌리는 사람을 위한 안내다. 같은 저장소의 주식 봇(`bot.py`, 키움증권)과는
**완전히 다른 프로그램**이다. 코드(`coin_bot.py`, `coin_sniper/`), 상태 폴더(`state/<mode>/`), 실행 명령이 따로다.
둘이 함께 쓰는 것은 `.env` 파일과 `origin/dashboard` 브랜치뿐이며, 둘 다 아래에서 주의점을 설명한다.

- 거래소: 바이낸스 **현물**, USDT 마켓, **매수 후 매도(롱)만** 한다. 공매도·선물·레버리지는 없다.
- 모드: `demo`(바이낸스 데모 환경, 기본값)와 `live`(실거래). 모의 체결 경로는 따로 없다. 데모 환경이 그 역할을 한다.
- 원칙: 확인하지 못한 것은 "모름"이다. 모르면 신규 매수를 하지 않는다(fail-closed, 아래 「중단 사유」).
  보유 종목의 청산 감시는 어떤 중단에서도 계속한다.
- 설계 근거: `docs/superpowers/specs/2026-11-17-coin-sniper-design.md`.

> 어떤 설정도 수익을 보장하지 않는다. 전략 수치는 검증되지 않은 출발값이다(아래 「한계」).

## 1. 필요한 것

- Python 3.10 이상(개발·테스트는 3.13). 윈도우와 리눅스에서 동작한다.
- 외부 패키지는 `websockets` 하나(`requirements.txt`).
- 바이낸스 데모 모드 API 키(데모 운영) 또는 실거래 API 키(실거래 운영).
- `AUTO_GIT_PUSH=true`로 대시보드를 게시하려면 이 저장소의 `origin`에 push할 수 있는 git 설정.

## 2. 설치

```bash
python -m venv venv
# 리눅스/macOS: source venv/bin/activate      윈도우: venv\Scripts\activate
python -m pip install -r requirements.txt
```

테스트(네트워크·키 불필요):


## 3. `.env` 설정

저장소 맨 위의 `.env`에 둔다(`.env.example` 참고). 이미 환경 변수로 들어 있는 값은 `.env`가 덮어쓰지 않는다.

| 항목 | 기본값 | 의미 |
|---|---|---|
| `MODE` | `demo` | `demo` 또는 `live`. 그 밖의 값이면 실행을 거부한다. |
| `BINANCE_DEMO_API_KEY` / `BINANCE_DEMO_API_SECRET` | 없음 | `MODE=demo`일 때 쓰는 키. 비어 있거나 `your_`로 시작하면 `run`·`reconcile`이 거부한다(종료 코드 2). |
| `BINANCE_LIVE_API_KEY` / `BINANCE_LIVE_API_SECRET` | 없음 | `MODE=live`일 때 쓰는 키. 출금 권한은 주지 말 것. |
| `LIVE_TRADING_ENABLED` | `false` | `MODE=live`는 이 값이 `true`일 때만 실행된다. |
| `STARTING_CAPITAL_USDT` | `1000` | 봇의 가상 계좌 시작 자본(USDT). 처음 실행할 때 상태에 저장되며, 그 뒤에는 `reconcile --reset-capital`로만 다시 반영된다. |
| `AUTO_GIT_PUSH` | `false` | `true`면 대시보드를 `origin/dashboard` 브랜치에 게시한다. |

주의:

- **공개 저장소에서 `AUTO_GIT_PUSH=true`면 보유 종목·체결 내역·평가액이 공개된다.** 키·시크릿·계좌 식별정보는 게시하지 않는다.
- `.env`는 주식 봇과 같이 쓴다. `LIVE_TRADING_ENABLED`와 `AUTO_GIT_PUSH`는 **두 봇에 함께 적용된다.**
  - 주식 봇 때문에 `LIVE_TRADING_ENABLED=true`인 상태라면, 코인 봇은 `MODE=live`와 실거래 키를 넣는 순간 실거래가 된다.
    `MODE`는 기본값(`demo`)으로 두거나 명시적으로 `demo`라고 적어 둔다.
  - 주식 봇의 `AUTO_GIT_PUSH` 기본값은 `true`, 코인 봇은 `false`다. 한 봇에만 다르게 주려면 그 프로세스의 환경 변수로
    직접 지정한다(예: 리눅스 `AUTO_GIT_PUSH=false python bot.py`). 환경 변수가 `.env`보다 우선한다.
- **두 봇은 같은 `origin/dashboard` 브랜치에 강제 push한다.** 둘 다 게시하면 서로의 대시보드를 덮어쓴다.
  동시에 돌릴 때는 한쪽만 게시하게 한다.

## 4. 0단계: 데모 환경 확인 (`python -m coin_sniper.probe`)

봇을 처음 돌리기 전에, 데모 환경이 봇이 가정하는 기능을 실제로 주는지 한 번 확인한다.

```bash
python -m coin_sniper.probe            # 결과 문서: docs/superpowers/specs/2026-11-17-demo-probe-results.md
python -m coin_sniper.probe --out 결과.md
```

- `MODE=demo`와 데모 키가 있어야 실행된다(아니면 종료 코드 2).
- 실제 거래는 **BTCUSDT를 최소 주문 금액의 3배만큼 시장가 매수하고, 받은 수량을 다시 파는 것**뿐이다. 다른 자산은 건드리지 않는다.
- 7개 항목을 차례로 실행하고, 하나가 실패해도 나머지를 계속한다. 전부 PASS면 종료 코드 0, 아니면 1.
  결과 문서에 항목별 관찰값과 「다음 조치」가 적힌다.

| # | 항목 | 확인하는 것 |
|---|---|---|
| 1 | 서버 시각과 계좌 조회 | 키로 서명 요청이 되는지, 서버와 로컬 시각 차이 |
| 2 | 초기 잔고 구성 | 데모 계정에 기본으로 들어 있는 자산 목록(참고용) |
| 3 | 감시 종목 후보 수 | USDT 거래 가능 종목 중 제외 규칙을 지나고 일봉 70개 이상·전일 거래대금 하한 이상인 종목이 5개 이상인지. 모든 후보의 일봉을 받으므로 몇 분 걸린다 |
| 4 | 시장가 매수 | 매수가 체결되는지, 수수료가 어느 자산에서 빠지는지, 최소 주문 금액 |
| 5 | 손절 주문 등록·조회·취소 | 거래소 손절 주문(STOP_LOSS_LIMIT)을 받는지 |
| 6 | 전량 시장가 매도 | 4번에서 받은 수량을 되팔 수 있는지 |
| 7 | 시세 스트림 | 데모 시세 WebSocket이 당일 시가·고가·저가·현재가를 주는지 |

실패했을 때(설계 문서 11절의 처리 표):

| 항목 | 실패 시 |
|---|---|
| 1. 키 발급 불가·인증 실패 | 멈추고 보고한다. 테스트넷이나 다른 거래소로 갈지는 소유자가 정한다 |
| 2. 손절 주문 불가 (probe의 5번) | 봇 감시만으로 진행한다: `coin_sniper/config.py`의 `PROTECTIVE_STOPS_ENABLED = False`. 대시보드에 "거래소 손절 주문 비활성" 경고가 상시 표시된다 |
| 3. 종목·거래대금 부족 | 조건을 통과한 종목만으로 진행한다(20개 미만 허용). 5개 미만이면 멈추고 보고한다(봇도 이 경우 신규 매수를 막는다) |
| 4. 피드에 당일 값 없음 (probe의 7번) | 설계상 대안은 같은 데모 주소의 REST 캔들로 당일 봉을 주기적으로 받는 피드다. **지금 코드에는 없다**: 봇을 돌리지 말고 보고한다 |
| 5, 6 (수수료 자산, 최소 주문 금액, 초기 잔고) | 관찰값을 설정과 문서에 반영하고 진행한다 |

probe의 6번이 실패하면 데모 계정에 BTC가 남았을 수 있다. 결과 문서의 「다음 조치」에 남은 주문 ID와 수량이 적힌다.
어떤 경우에도 데모 모드에서 실거래 주소의 시세를 섞어 쓰지 않는다.

## 5. 실행 (`python coin_bot.py run`)

```bash
python coin_bot.py run
```

- 전경에서 돈다. 멈출 때는 **Ctrl+C**("중지합니다"를 출력하고 종료 코드 0). 상태는 루프마다 저장되므로 따로 저장할 것은 없다.
- 시작할 때 모드, REST·시세 주소, 상태 폴더, 시작 자본, 게시 여부를 출력한다(키는 출력하지 않는다).
  시작 자본은 상태에 저장된 값(봇이 실제로 쓰는 값)과 구간 시작일이다. `.env`의 `STARTING_CAPITAL_USDT`가 그와 다르면
  "설정값 X USDT는 `reconcile --reset-capital` 실행 시 반영됩니다"를 덧붙인다. 첫 실행이면 `.env` 값을 "이 값으로 저장"이라고 표시한다.
  `live`면 "실거래 모드입니다. 실제 자금으로 실제 주문이 나갑니다" 경고를 크게 출력한다.
- 30초(`POLL_INTERVAL_SECONDS`)마다 루프를 시작한다(루프에 걸린 시간을 빼고 잔다). 루프마다 한 줄:

  ```text
  2026-11-17 19:00:30 KST | 정상 운영 | 평가액 1,000.00 USDT | 보유 0 | 중단: 없음 | 신규 매수 가능
  ```

  상태는 「정상 운영」「신규 매수 중단」(중단 사유 있음)「루프 오류」 중 하나, 평가액을 모르면 `-`.
  그 루프에서 새로 생긴 이벤트(BUY, SELL, SKIP, RISK, SYSTEM, ERROR)가 아래에 한 줄씩 붙는다.
- 대시보드 게시 실패는 "대시보드 게시 실패(매매는 계속)" 한 줄만 남기고 매매는 계속한다.
- 거부되는 경우(종료 코드 2): 설정 오류, 키 없음, 같은 모드의 봇이 이미 실행 중("이미 실행 중입니다"),
  상태 파일 손상(파일 이름을 출력한다. 빈 장부로 시작하지 않는다).
- 같은 모드로는 한 프로세스만 뜬다(`state/<mode>/coin_bot.lock`, OS 파일 잠금). 프로세스가 죽으면 OS가 잠금을 푼다.
  `demo`와 `live`는 상태 폴더와 잠금이 따로라 동시에 돌 수 있다.

### 서비스로 돌리기 (선택)

봇은 스스로 데몬이 되지 않는다. 운영체제의 서비스 관리자에 `python coin_bot.py run`을 맡긴다. 서비스 파일은 배포하지 않는다.

- **리눅스(systemd)**: 주식 봇의 `quant_sniper.service`와 같은 방식으로 유닛을 하나 만든다. 핵심은
  `WorkingDirectory=<저장소 경로>`, `ExecStart=<venv>/bin/python coin_bot.py run`, `Restart=on-failure`, `RestartSec=30`.
  중지는 `systemctl stop`(SIGTERM)이고, 상태는 루프마다 저장되어 있으므로 다음 시작 때 그대로 이어진다.
  로그는 `journalctl -u <유닛>`으로 본다.
- **윈도우(작업 스케줄러)**: "컴퓨터 시작 시" 트리거로 작업을 만들고, 프로그램은 venv의 `python.exe`, 인수는
  `coin_bot.py run`, 시작 위치는 저장소 폴더로 둔다. "실패 시 다시 시작"을 켜고, "작업이 이미 실행 중이면 새 인스턴스를 시작 안 함"으로 둔다
  (그래도 두 번째 프로세스는 잠금 때문에 바로 종료된다). 절전 모드에서 깨우지 않으면 그동안은 「봇 꺼짐 시간」으로 기록된다.

봇이 멈춰 있는 동안에도 거래소 손절 주문(보호 주문)은 거래소에 남아 손절을 실행한다. 단 보호선 상향, 고점 추적, 타임스탑은 봇이 돌아야 한다.

## 6. 상태 보기 (`python coin_bot.py status`)

```bash
python coin_bot.py status
```

키도 네트워크도 쓰지 않고 `state/<mode>/`의 저장 상태만 읽는다(읽기만 하므로 봇이 도는 중에도 실행할 수 있다).

- 모드, 마지막 정상 루프 시각(KST), 시작 자본·실현 손익·가상 현금·구간 시작
- 보유 포지션(수량, 매수가, 현재 보호선, 진입 시각)
- 중단 사유(코드, 상세, 시작 시각 KST). 마지막으로 저장된 값이며, 봇이 꺼져 있으면 다음 실행 때 다시 판정된다.
- 진행 중 주문 기록(체결 확인 전인 주문)

상태 폴더가 없으면 "아직 실행 기록이 없습니다"(종료 코드 0), 상태 파일이 손상됐으면 파일 이름을 출력하고 종료 코드 2.

## 7. 수동 정리 (`python coin_bot.py reconcile`)

### 언제 쓰나

장부(봇이 기록한 포지션)에는 있는데 거래소 잔고에는 없는 포지션이 생겼을 때다. 봇은 이런 포지션을 스스로 지우지 않는다
(추정으로 장부를 고치면 "체결 기준 장부" 원칙이 깨진다). 이때는 「계좌·장부 불일치」(`recon_mismatch`)로 신규 매수가 멈춘다.
청산 감시는 계속하므로, 그 포지션이 손절선 등에 닿으면 매도를 보내고 거래소가 잔고 부족으로 거절한다(위험 이벤트로 남는다).
10분이 지나도 풀리지 않으면 대시보드에 "수동 정리 필요"가 뜬다.

- **데모 잔고 초기화**: 바이낸스 데모 계정을 초기화하면 보유 코인이 사라진다.
- **사람이 직접 매도**: 거래소 앱에서 봇의 코인을 직접 판 경우.

거래소에서 코인이 사라진 이유가 **봇 자신의 주문**일 수도 있다. 봇이 꺼져 있는 동안 거래소 손절 주문이 체결됐거나,
매도 주문을 보낸 뒤 체결 확인 전에 봇이 멈춘 경우다. 이런 체결은 봇이 다음 실행 때 주문 조회로 찾아 장부에 정상 매도로 반영한다
(매도 대금이 가상 현금과 통계에 들어간다). 그래서 수동 정리보다 **봇 실행이 먼저**다.

### 순서

1. 먼저 봇을 실행한다(`python coin_bot.py run`). 미결 주문과 체결된 거래소 손절은 봇이 스스로 정리한다.
2. `recon_mismatch`가 계속 남고 대시보드에 "수동 정리 필요"가 뜰 때(불일치가 10분 넘게 지속)만 다음으로 간다.
3. 봇을 멈춘다. 봇이 도는 중이면 `reconcile`은 "이미 실행 중입니다"로 거부한다(종료 코드 2).
4. 거래소에서 그 종목의 미체결 주문(봇의 손절 주문 등)이 남아 있는지 보고, 남아 있으면 직접 취소한다. **이 명령은 거래소에 아무 주문도 보내지 않는다.**
5. 실행:

   ```bash
   python coin_bot.py reconcile                    # 계획을 보여 주고 "진행할까요? [y/N]"를 묻는다
   python coin_bot.py reconcile --yes              # 묻지 않고 진행
   python coin_bot.py reconcile --reset-capital    # 정리 + 시작 자본 재설정
   ```

6. 봇을 다시 시작한다. 불일치 중단은 다음 루프의 판정으로 풀린다.

### 무엇을 하나

- 거래소 계좌 조회가 실패하면 장부를 건드리지 않고 끝난다(종료 코드 1).
- 각 장부 포지션을 거래소의 (사용 가능 + 잠김) 수량과 비교한다. 거래소 수량이 **장부 수량 − 수량 단위 1스텝**보다 적으면
  "없는 포지션"이다. 봇의 대조와 같은 기준이다. 종목 규칙을 받지 못하면 허용 오차 0으로 판정하고 그렇다고 출력한다.
- 계획(종목별 장부 수량 / 거래소 수량 / 정리 또는 유지, 시작 자본 재설정 여부)을 먼저 출력하고 확인을 받는다.
  `y` 또는 `Y`가 아니면(질문 중 Ctrl+C 포함, "중단: 변경 없음") 아무것도 바꾸지 않고 종료 코드 1.
- 없는 포지션이라도 그 종목에 **진행 중 주문 기록이 있거나 보호 주문 기록(`protective`)이 남아 있으면 정리하지 않는다.**
  계획에 "보류: 미결 주문/보호 주문 기록 있음 — 봇을 먼저 실행해 정리되게 하세요"로 표시하고 포지션·주문 기록을 그대로 둔다.
  봇의 체결일 수 있는 것을 손실로 처리하지 않기 위해서다. 나머지 없는 포지션은 정리한다. 보류된 종목만 있으면 아무것도 바꾸지 않는다(종료 코드 0).
- 정리하는 포지션마다:
  - 장부에서 포지션을 지운다.
  - 체결 기록에 매도 한 건을 남긴다: 사유 "수동 정리", 가격 0, 손익 0, `counted: false`(통계 제외),
    `dust_writeoff` = 그 포지션의 매수 원가.
  - **그 원가만큼 실현 손익을 줄인다.** 코인은 이미 없어졌으므로 가상 현금(시작 자본 + 실현 손익 − 보유 원가)이 늘어나면 안 된다.
    그래서 정리 전후의 가상 현금은 같고, 평가액은 그 포지션의 평가액만큼 줄어든다.
- 거래소와 맞는 포지션은 그대로 둔다. 정리할 것이 없고 `--reset-capital`도 없으면 "정리할 포지션이 없습니다"(종료 코드 0, 변경 없음).
- 하나라도 정리했거나 `--reset-capital`이면 수익률 구간 시작(`segment_start`)을 지금으로 바꾼다
  (대시보드의 「시작 자본 대비 (날짜부터)」).
- 이벤트에 SYSTEM "수동 정리: <종목들>"(재설정이면 "; 시작 자본 재설정")을 남긴다.

### `--reset-capital`

실현 손익을 0으로, 시작 자본을 지금의 `STARTING_CAPITAL_USDT` 값으로, 고점 평가액을 시작 자본으로 되돌리고,
오늘의 기준 평가액과 기록 대기 중인 평가액 줄을 비운다.

- **정리 뒤에도 장부에 포지션이 남아 있으면(보류된 종목 포함) 거부한다**(종료 코드 1). 남은 포지션의 원가가 새 자본에 이중으로 계산되기 때문이다.
- 데모 잔고를 초기화해서 포지션이 전부 사라졌다면 `reconcile --reset-capital` 한 번으로 정리와 재설정을 같이 한다.

### 통계에 미치는 영향

- 「누적 성과」(청산 수, 승률, 평균 이익·손실, Profit Factor, 최대 낙폭, 최대 연속 손실, 누적 순손익)와 「전략별」에서 빠진다.
- 평가액·「시작 자본 대비」 수익률·기간별 수익률에는 원가만큼의 손실로 반영된다(재설정하면 시작 자본 대비는 새로 시작한다).
- 재설정하지 않으면 고점 평가액과 오늘의 기준 평가액이 그대로라서, 정리한 원가가 크면 「낙폭 한도」(-12%)나
  「일일 손실 한도」(-4%)가 걸려 신규 매수가 멈출 수 있다. 포지션이 모두 없어졌다면 `--reset-capital`을 쓴다.
- 평가액 기록(`equity_history`)은 지우지 않는다. 「첫 기록 대비」 등 기간별 수익률은 재설정 이전 기록과도 비교된다.

## 8. 대시보드

`AUTO_GIT_PUSH=true`일 때만 게시한다. 세 파일(`README.md`, `dashboard_state.json`, `dashboard_events.json`)을
부모 없는 단일 커밋으로 만들어 **`origin/dashboard` 브랜치에 강제 push**한다(이력은 남지 않는다). 작업 파일은 `state/<mode>/dashboard/`에 쓴다.

- 게시 주기: 체결·위험·오류 이벤트(BUY, SELL, RISK, ERROR)나 중단 사유 변화는 즉시, 그 밖의 변화가 있거나 보유 중이면 5분마다,
  변화가 없어도 30분마다.
- 게시가 실패하면 5분 동안 다시 시도하지 않는다. git 명령 하나는 최대 60초, 자격 증명을 묻지 않는다. 실패해도 매매는 계속한다.
- git은 장부가 아니다. 장부는 로컬 `state/<mode>/`에만 있다.
- 맨 위 제목에 모드(`[DEMO]`/`[LIVE]`), 시각은 모두 KST다.

### 1. 현재 상태

- 상태(정상 운영 / 신규 매수 중단 / 루프 오류), 신규 매수 가능 여부, 보유 종목 수, 평가액, 현금(가상 계좌).
- 중단 사유 표: 사유, 상세, 시작 시각. 불일치가 10분을 넘으면 "수동 정리 필요: `python coin_bot.py reconcile`".
- 장부에 없는 거래소 잔고(봇이 사지 않은 자산), 거래소 손절 주문 비활성 경고(해당할 때).
- 시스템 신선도: 시세 연결, 마지막 시세(BTCUSDT 수신 시각), 마지막 계좌 조회, 마지막 정상 루프, 실행 커밋.
- 오늘의 감시: 기준일(UTC), 감시 종목 수, 지금 수량 기준으로 매수 가능한 종목 수. 종목별 현재가·최대 수량·매수 가능성.
  최대 수량은 **손절폭 4%(`MIN_STOP_LOSS_PCT`)를 가정한 표시용 추정**이다. 실제 주문 수량은 신호의 손절폭으로 정한다.
- 신호 확인 단계: 종목·전략별 연속 확인 횟수(3회가 되면 주문).
- 위험 관리:
  - 고점 대비 낙폭 = (고점 평가액 − 지금 평가액) / 고점 평가액.
  - 일일 손실 한도 기준 수익률 = 지금 평가액 / **오늘(UTC) 첫 평가액** − 1.
  - 주문 배율: 낙폭 8% 이상이면 50%, 아니면 100%.
  - 열린 위험 합계 = Σ max(0, 매수가 − 현재 보호선) × 수량 / 평가액.
  - 남은 슬롯 = 3 − 보유 수 − 진행 중 매수 주문 수.
- 보유 포지션: 수량, 매수가, 현재가, 수익률(현재가 / 매수가 − 1, 수수료 미반영), 최초 손절가, 현재 보호선,
  거래소 손절 주문(on / off / disabled, 취소 확인 중), 타임스탑까지 남은 시간(진입부터 168시간), 고점 추적 여부.

### 2. 수익률

평가액 = 가상 현금 + Σ 보유 수량 × 현재가. 가상 현금 = 시작 자본 + 실현 손익 − 보유 원가.
봇이 사지 않은 자산과 시작 자본을 넘는 거래소 잔고는 넣지 않는다.

- 기간별(봇 / BTC 보유):
  - 평가액 기록은 UTC 날짜가 바뀔 때, 전날 마지막으로 계산한 평가액과 그날 BTCUSDT 일봉 종가를 한 줄로 남긴다.
    봇이 꺼져 있던 날은 줄이 없다.
  - 「전일 대비」「7행 전 대비」「30행 전 대비」는 기록을 **끝에서부터 세어 1번째·7번째·30번째 줄**과 비교한다
    (「전일 대비」는 마지막 줄, 달력 일수가 아니다).
    기준일이 그보다 오래됐으면 "기록 누락 있음"을 붙인다. 「첫 기록 대비」는 첫 줄과 비교한다.
  - 봇 = 지금 평가액 / 기준 줄 평가액 − 1. BTC 보유 = 지금 BTCUSDT 시세 / 기준 줄 BTC 종가 − 1.
  - 「시작 자본 대비 (날짜부터)」 = 지금 평가액 / 시작 자본 − 1. 날짜는 구간 시작일(처음 실행, 또는 마지막 수동 정리·재설정).
- 누적 성과: 청산 1건 = 매도 기록 1건(부분 매도도 각각). 잔량 정리·수동 정리(`counted: false`)는 뺀다.
  - 승률 = 순손익 > 0인 청산 비율. 평균 이익·손실 = 순수익률(%)의 평균.
  - Profit Factor = 이익 청산 순손익 합 / 손실 청산 순손실 합.
  - 최대 낙폭 = 누적 순손익 곡선의 고점 대비 최대 하락 / 시작 자본.
  - 누적 수수료: 모든 체결(통계 제외 포함)의 USDT 수수료 + 기초 자산 수수료 × 체결가. 그 밖의 자산(BNB 등)은 값을 매기지 않고 따로 표시한다.
  - 평균 슬리피지: 주문 직전 시세 대비 체결가 차이(%)의 평균.
- 전략별: RSI 회복 / 변동성 돌파 각각의 청산 수, 승률, 평균 수익률.
- 주간 평가액: 평가액 기록 중 일요일(UTC) 줄 최근 12개와 직전 일요일 줄 대비 수익률.
- 데모 모드에서는 "데모 가격은 실거래소와 유사하지만 같지 않음"을 표시한다.

### 3. 오류율

열은 「오늘(UTC 0시~)」「7일」(오늘 포함 7개 UTC 날짜)「전체」(지표가 있는 첫날부터). 지표는 UTC 날짜별로 쌓고 400일 보관한다.

- API 호출·실패율: 바이낸스 REST 어댑터를 거친 모든 호출 중 실패 비율. 일시적(네트워크, 5xx, 호출 한도, 점검)과 확정적(잔고 부족, 규칙 위반 등) 구분.
- 주문: 전송 / 거절 / 체결 미확인 / 부분 체결 건수.
- 시세 재연결 횟수, 시세 끊김 시간.
- 가동률 = 정상 완료 루프 수 × 30초 / 그 기간의 경과 시간(오늘은 UTC 0시부터 지금까지), 최대 100%.
- 중단 시간(사유별 상위 5): 루프마다 걸려 있던 사유에 루프 간격(최대 60초)을 더한다.
- 봇 꺼짐 시간: 재시작 때 마지막 정상 루프와의 차이가 60초를 넘으면 그 차이를 더한다. 재시작 횟수, 루프 예외 횟수.

### 4. 최근 7일 이벤트

매수, 매도, 스킵, 위험, 시스템, 오류 이벤트. 최근 100건을 보여 준다. 반복되는 스킵·위험은 한 줄의 「반복」 횟수로 합친다.

## 9. fail-closed: 중단 사유

중단 사유가 하나라도 있으면 **신규 매수만** 멈춘다. 청산 감시, 보호 손절 주문 관리, 진행 중 주문 확인은 계속한다
(예외: 호출 한도 대기 중에는 거래소를 전혀 부르지 않는다). 사유는 `state/<mode>/halts.json`에 저장되어 재시작해도 남고
(`fatal`만 예외, 아래 표), 다음 루프의 판정으로 풀린다. 이 밖에 UTC 0시~0시 15분, 보유 3종목, 종목 규칙 미확보일 때도 신규 매수를 하지 않는다.

| 코드 | 걸리는 때 | 풀리는 때 |
|---|---|---|
| `account_fetch` | 계좌 조회 실패 | 다음 계좌 조회 성공 |
| `feed_stale` | 시세 연결 끊김, BTCUSDT 또는 보유 종목 시세가 15초 넘게 없음 | 다음 판정에서 모두 정상 |
| `maintenance` | 주문 전송이 일시적 오류로 실패(점검 등) | 다음 계좌 조회 성공 |
| `rate_limit` | 호출 한도 응답(HTTP 429/418) | 거래소가 알려 준 시간(없으면 60초)이 지난 뒤 첫 루프 |
| `universe` | 오늘(UTC) 감시 종목이 없거나 5개 미만, 또는 종목 규칙 미확보 | 재시도(10분 간격) 성공, 또는 다음 UTC 날짜의 선정 성공 |
| `daily_loss` | 평가액이 오늘 첫 평가액 대비 -4% 이하 | 다음 UTC 날짜 |
| `drawdown` | 평가액이 고점 대비 -12% 이하 | 매 루프 다시 계산해서 한도 위로 회복 |
| `recon_mismatch` | 거래소 (사용 가능 + 잠김) < 장부 수량 − 1스텝인 보유 종목 | 대조가 다시 맞음. 안 맞으면 수동 정리(7절) |
| `order_unconfirmed` | 체결을 확인하지 못한 주문 기록이 남음 | 남은 주문 기록이 모두 확정되거나 지워짐 |
| `protective_cancel` | 보호 손절 주문 취소 실패, 또는 취소한 주문의 최종 상태 미확인 | 그 주문의 최종 상태가 확인되어 장부에 반영됨 |
| `fatal` | 확정 오류: HTTP 401/403, 바이낸스 오류 코드 -2014·-2015(키 형식·키·IP·권한) | 봇이 도는 동안에는 풀리지 않는다. 원인(키·권한·IP)을 고친 뒤 재시작하면 풀린다. 원인이 남아 있으면 첫 호출에서 다시 걸린다 |
| `loop_error` | 루프의 한 단계에서 예외 | 예외 없이 끝난 다음 루프 |

> `fatal`: 원인(키·권한·IP)을 고친 뒤 재시작하면 풀린다(SYSTEM 이벤트 "재시작으로 치명적 중단 해제"). 원인이 남아 있으면 첫 호출에서 다시 걸린다.

체결 미확인이나 보호 주문 취소가 계속 풀리지 않으면 거래소에서 그 주문의 상태를 직접 확인한다.

## 10. 한계

- **데모 시세는 실거래소와 비슷하지만 같지 않다.** 체결가, 거래대금, 감시 종목이 실거래와 다르다.
- 전략·리스크 수치(`coin_sniper/config.py`)는 코인 변동성에 맞춘 **검증되지 않은 출발값**이다. 2단계 백테스트로 다시 잡을 예정이다.
- 현물 매수 후 매도(롱)만 한다. 하락장에서는 시장 필터(BTC가 상승 중인 60일선 위) 때문에 거의 매수하지 않는다.
- 데모 계정에 기본 지급된 코인처럼 **장부에 없는 거래 가능한 잔고가 있는 종목은 신규 매수를 건너뛴다**
  ("거래소에 미관리 잔고 있음"). 늦게 체결된 매수를 두 번 사지 않기 위한 안전장치다.
- 봇이 꺼져 있으면 거래소 손절 주문만 동작한다. 보호선 상향·고점 추적·타임스탑은 봇이 돌 때만 한다.
- 수익을 보장하는 것은 없다. 실거래는 손실을 감당할 수 있는 금액으로만 한다.

## 11. 보안

- `.env`는 절대 커밋하지 않는다(`.gitignore`에 있다). 키와 시크릿은 `.env` 또는 환경 변수에만 둔다.
- 키·시크릿·서명은 콘솔, 로그, 이벤트, 대시보드, 상태 파일 어디에도 쓰지 않는다. 시작 화면에도 주소만 출력한다.
- 실거래 키에는 출금 권한을 주지 말고, 가능하면 IP 제한을 건다.
- `demo`와 `live`는 키, 주소, 상태 폴더(`state/demo`, `state/live`), 잠금 파일이 모두 따로다. `state/`도 커밋되지 않는다.
